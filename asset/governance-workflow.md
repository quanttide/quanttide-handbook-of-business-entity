# 大规模集中治理工作流程

适用于一次性处理大量文档创建、重构或迁移的场景。

## 整体策略

集中治理的核心策略是**先铺底座，再精雕细琢**。在一次会话中完成所有文件的结构性变更，不追求一次完美。底座铺完后，后续按单一任务推进日常维护。

## 工作流程

### 第一步：确定来源与目标

明确来源文件和目标仓库。来源通常是 `apps/qtadmin-private/docs/` 下的草稿或示例文件，目标根据内容性质分三类：

- 结构性规则 → **章程**（`bylaw/`）：章-条结构，法律化表述，定义权责
- 操作指引 → **手册**（`handbook/`）：极简，只说怎么做，不解释为什么
- 原理讲解 → **教程**（`tutorial/`）：叙事驱动，解释为什么，含设计者注

同一来源内容可能需要同时产出三类文件。先章程定规则，再手册写操作，再教程讲原理。

### 第二步：按风格模板转换

**章程格式**（参考 `organization/position/company-representative.md`）：

- 第一章 总则（制定依据、目的、适用范围、原则）
- 中间章节按制度维度组织（职权/职责、等级/分类、程序/流程）
- 末章 附则（章程效力、解释权）
- 条款使用「第X条」编号，连续不跳号
- 内部引用格式：「按本章第X条」

**手册格式**（参考 `handbook/organization/company-representative.md`）：

- 场景驱动，按履职场景组织
- 只说怎么做，不解释为什么
- 操作要点 + 注意事项结构
- 用引用块（> 设计者注：）补充设计意图
- 段落为主，列表为辅

**教程格式**（参考 `tutorial/organization/company-representative.md`）：

- 叙事驱动，从真实经历或常见困惑开场
- 第二人称（你），营造对话感
- 解释"为什么"，讲背后的设计逻辑和思考历程
- 关键处用设计者注补充决策内幕
- 末节收束，总结核心洞见

### 第三步：提交与同步

每个仓库独立维护。修改完成后按以下顺序提交：

```
子模块内 git add → git commit → git push
父仓库     git add 子模块路径 → git commit → git push
```

两步缺一不可。提交信息使用 Conventional Commits 格式。

### 第四步：更新目录结构

新增文件后，同步更新对应仓库的 `myst.yml` TOC。按内容分组新增章节，确保新文件可在导航中访问。

## 常见注意事项

- 不要在父仓库直接修改子模块文件，进子模块目录操作
- 文件重命名用 `mv` 后需同步 git 操作（`git rm` 旧文件 + `git add` 新文件）
- `git restore` 会从索引恢复文件，可能导致多余文件残留
- 一次会话控制在单一子模块内变更，避免跨子模块操作增加认知负荷
- 底座铺完后，后续按单一任务推进，不要重复大规模模式
