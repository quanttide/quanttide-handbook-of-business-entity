# 智能体工程工作手册

## 核心理念

整个 AIGC 相关的工程领域不需要从零开始构建，当成基础设施使用即可。核心工作是管理好提示词、上下文和智能体的生命周期。

## 三大领域

| 领域 | 说明 |
|---|---|
| **提示词工程** | 严格管理提示词的生命周期——编写、测试、版本化、废弃 |
| **上下文工程** | 管理与 AI 交互的上下文信息，确保信息完整且有效 |
| **智能体工程** | 智能体的构建、配置和协作 |

## 技能工程

技能（Skill）是将实践经验固化为可复用的流程模板。

### 从对话中提炼 Skill

1. 使用一个纯净的对话完整地做一遍事情
2. 结束时复盘方法
3. 将方法提炼到项目的 Skill 文件中

在纯净对话中，只做一件事情且由 AI 接管，人类只让 AI 按既定流程执行。这样的环境能干净地捕捉人类的隐式知识。

### 为 Skill 准确命名和分类

- **分类**：遵循标准领域划分（编程 code、写作 write、数字资产 asset、数据工程 data、文档工程 docs 等）
- **命名**：简单直接（发布 release、计划 plan、设计 design、格式 format），建议领域名称作为前缀（如 docs-format）
- 人类可以不纠结 Skill 的具体文本，但必须维护好命名、描述等元数据

### 只保留有效的 Skill

低质量的 Skill 对人和 AI 都是负担，应及时抛弃：

- 流程不完善的 → 回到人机交互模式摸索
- 机制不合适的 → 考虑内置为自动化工具
- **舒适区**：规则引擎不够灵活但又存在标准规范的流程（如 Git 的 commit/release、TDD 流程）→ 最大限度 Skill 化

> 设计者注：AIGC 时代的核心能力不是"写提示词"，而是"管理 AI 交互的全生命周期"。提示词只是接口，真正决定产出质量的是上下文的质量和智能体的架构设计。Skill 是你和 AI 的默契——写一次，用无数次。但要记住，Skill 的质量比数量重要，一个精心打磨的 Skill 胜过一百个凑合的。

## 附录：智能体工程检查清单

- [ ] 当前任务的提示词是否有版本管理？
- [ ] 上下文信息是否完整且无冗余？
- [ ] 是否需要构建智能体来协作了？
- [ ] 最近的实践是否能提炼为 Skill？
- [ ] Skill 的命名和分类是否准确？

## 手册使用建议

1. 提示词、上下文和智能体是三个层次——先管好提示词，再优化上下文，最后才考虑智能体。
2. Skill 从实际工作中总结，让 AI 自己写——人类手动维护的 Skill 大多缺乏必要细节。
3. 手册不替代章程：正式 AI 工程制度以章程为准。
